# AMP Verse server analysis and shared database

Owner architecture, 2026-11-19. This document distinguishes implemented foundations from the remaining integration work.

## Modular installation and list-centered library: owner decisions

The server is a standalone install on Windows or Linux, with no desktop UI required to keep services running. Desktop and Android are optional client components with plug-in capabilities: install the full suite on one machine or just selected pieces per device. Native Android/Desktop packaging and plug-in interfaces must be specified explicitly; this is not a claim that one binary plug-in runs unchanged on every OS. A minimal client host provides identity, connection/configuration, navigation and playback ownership, while selected capabilities are installed/enabled as modules. Shared state/protocols and module compatibility versions must be explicit. Modules should not require installing the whole feature set or duplicate the authoritative server database. Existing local playback/offline behavior and one-Cast-session client rules remain intact. Android does not gain heavy analysis by installing a UI module.

Library management is the sole owner of physical folder organization. Playlists, Smart Playlists, categories, annotations, search and analysis NEVER move/rename source files or restructure folders. Library organization jobs follow explicit owner rules and preserve protected audio/spoken-word folders. One physical track may belong to many lists without file duplication. Normal lists carry explicit membership/order; Smart lists carry powerful saved rules and eligible-song views.

Search in manual DJ browsing acts as a filter on the current library folder or playlist, matching any indexed metadata (title, artist, album, genre, tags, comments, filename, categories and annotations). Example: edm matches any indexed field containing edm. Clearing restores the view. Search never changes membership, saved order or playback. Track selection can load a matching result into a deck. Normalize case and document matching behavior; do not infer genre from unknown files.

Categories are multi-label annotations, separate from physical folders. Suggested dimensions reflect owner examples: vocal content (Acapella, Instrumental, Full Mix, Unknown), origin (AI-generated, Suspected AI, Unknown), type/version (Song, Clip, Stem, Remix, Live, Intro/Extended Edit), and useful notes (Clean/Explicit, reviewed analysis, uncertain identification). One track may be Clip + Instrumental + AI-generated. Labels/badges are visible and indexed for ordinary search, Smart rules and manual filters; synchronize them with provenance/revisions and allow owner correction. Exact dimension/name choices remain UI design details; no AI detection accuracy claim is made.

Editor creates CLIPS with source association and selected time range. Clips have their own identities, preparation/analysis and visible Clip label. Clip analysis does not overwrite parent-track analysis. BPM/key/beats/energy/stems apply when meaningful, with source/version/sample-range provenance.

AI-generated music is identified/annotated/filtered, NOT generated by AMP Verse. Unknown/unmatched metadata is not proof of AI generation; rare recordings, remixes and instrumentals can be absent online. Any detector output is uncertain and needs confidence/override. Owner-confirmed AI-generated material can skip futile catalog-identification lookup and use server analysis. Instrumental status alone must not suppress valid online lookup. Generated instrumental versions link to their original source and retain separate analysis. No default exclusion or automatic relabeling of existing music without reviewed evidence.

## Module responsibilities and integration placement: owner clarification

Library is the music manager: physical folder organization, metadata, playlists, server analysis orchestration and media sync. Cast/Remote is the radio/remote unit: audio sending/receiving, station connections, playback/output control, and the Home Assistant/Node-RED integration surface. DJ is manual mixing and Auto Mix using prepared data. Lab creates clips, downloads/imports media and hands results to Library. Player is basic playback. Podcasts manages subscriptions/episodes/downloads/listening state.

Companion means specifically BITFOCUS COMPANION integration, not a general-purpose automation builder. It supplies button actions and actual-state feedback: play songs/stations, load playlists/DJ mixes, trigger actions, control DJ/Auto Mix, and connect live DJ output to the server/mixer for an event. Bitfocus Companion integration is available on BOTH DESKTOP AND SERVER, not Android. It can target the applicable local installation or an authorized remote AMP endpoint. Keep connection/credential ownership explicit and avoid duplicate button actions/feedback loops across installations.

The Home Assistant/Node-RED connectors execute ONLY ON THE SERVER. Store their credentials, subscriptions, callbacks and integration/automation sessions server-side. Do not host those connectors/background integration services on desktop or Android. Desktop/mobile remain controllable endpoints and expose the needed AMP commands/status through the agreed protocol. Cast audio send/receive still runs on the applicable endpoint under its one-active-session rule; this connector placement does not remove client audio endpoint capabilities.

UI, HA/Node-RED and Bitfocus use the same versioned commands/state, preserving playback ownership, cue privacy, authorization and clear failures when a target is offline. The latest owner clarification explicitly overrides the earlier server-only statement for BITFOCUS only; HA/Node-RED remain server-only.

## Bitfocus Companion action coverage

On desktop and server, Companion exposes the available AMP Verse capabilities as configurable Bitfocus actions with real-state feedback. Coverage includes:

- Music/player: select/play a song, pause/resume/stop, seek where supported, queue operations, output/volume.
- Clips: select/trigger/stop a clip and route it through the applicable player/DJ/sampler path. A clip trigger must state its target/bus rather than silently replace an unrelated live mix.
- Playlists: choose/load normal or Smart Playlists, play or send to DJ, and explicit ordered/shuffle behavior. Automated station hosting remains server-only; normal playlists preserve saved order unless Shuffle is on.
- DJ: load tracks or a saved mix, transport/cue/Auto Mix controls and configured performance actions. Preserve private cue and manual locks.
- Cast/radio: select a target, start/stop a live send or receive, connect to a server-hosted station, choose physical output and report actual connection/buffering/error state. Respect one active sending OR receiving session on desktop/mobile and never steal a newer owner silently.
- Remote: target an authorized AMP installation, issue its supported commands, retrieve state and trigger configured remote functions. Show the selected local/remote target clearly.

Use one versioned command/capability/state model with the apps rather than inventing independent playback logic for Bitfocus. Bind buttons to stable song/clip/playlist/station/device IDs, not transient list row indices. Distinguish Load from Play and one-shot actions from stateful toggles. Match action availability to installed modules and target capabilities. Handle unavailable/offline targets explicitly, prevent duplicate/replayed triggers on reconnect, and show success only from acknowledged/observed state. Keep feedback loops from triggering actions recursively. Button feedback includes playback, loaded item/mix, selected output, station/cast ownership and connection/error state. Validate cross-module event scenarios with actual target state, not only HTTP acceptance.

This is the requested integration scope, not a claim every listed action is already implemented.

## Product split

The server is the always-on music hub, library authority and primary preparation machine: discover completed imports from Lidarr, the downloader, folders, or other import paths; identify the exact recording; reuse existing information; compute missing features and stems; refine with approved web providers; publish versioned prepared results.

Server playback/mixing has a simple, mobile-like surface: Player, Library/Smart Playlists, Auto Mix, queue and outputs. It can play/mix independently of an open desktop. It must also host persistent virtual stations backed by Smart Playlists, with station-specific queues, mixing rules, controls and listener state. Multiple stations require independent playback owners and isolation; the current Cast implementation advertises one station per server, so multi-station hosting is a remaining architectural change, not a shipped capability.

Server music management receives completed Lidarr/download jobs, desktop uploads and folder imports through one intake path. It sorts and maintains the master library according to the owner's organization/exclusion rules, indexes it and prepares it. Uploads land in staging and are validated before publication; duplicate/conflict handling must not silently overwrite or delete existing audio. Downloader source support must follow the source's supported access method.

Desktop is a lighter performance workstation: VirtualDJ/Mixxx-style browsing, cueing, manual mixing and Auto Mix consume prepared database records. Desktop may write reviewed corrections and explicit preparation results. Full-library background preparation belongs on the server. Offline desktop performance uses cached prepared data. Audio can be read directly from a LAN share or deliberately downloaded/synced to local storage. A desktop download can later be uploaded/imported into the master library. Show file availability and active playback location clearly; sync must be resumable and explicit about direction, version conflicts and deletions.

Mobile has the simple playback/mixing and station-browsing experience, and reads/caches prepared data for playback, mixing and offline use. It does not run the analysis engine or publish analysis corrections. Local playback state/offline queues are separate from shared analysis writes. Existing mobile features that can edit preparation must be audited before claiming this access split is enforced everywhere.

The browser is a control/view surface. Analysis jobs run on the server, not in the browser audio callback. Server and desktop share track identities and preparation semantics instead of inventing different analysis formats.

## Shared playlists and media sync

Normal playlists and Smart Playlist rules synchronize bidirectionally across server, desktop and Android. Mobile read-only access refers to ANALYSIS, not playlist editing. Preserve stable IDs, revisions, offline edits, ordering, rename/delete behavior, conflicts and existing playlist data. Do not silently overwrite a concurrent edit. Keep shared rules separate from each device's available media/selection. Playlist metadata sync is distinct from downloading/syncing audio files.

## Cast: universal routing and laptop master to physical mixer

A required performance scenario is desktop DJ MASTER AUDIO -> LAN -> server receiver -> selected server physical audio device -> external mixer. The desktop performs the live mix; the server plays the finished stream without recreating it from track/playlist events. Preserve local headphone/private cue unless explicitly routed. The server's web controls expose the local output, receiver state, volume, stop/reconnect and honest buffering/latency telemetry. Independent server Smart Radio, Google-speaker casting, remote control and file sync remain separate capabilities. High-performance mode needs measured end-to-end latency/dropout/clock-drift testing; buffer targets are not measurements. Reconnection discards stale backlog and resumes current live audio.

Universal Cast scope: desktop, Android and server AMP apps can SEND and RECEIVE supported audio. External output adapters include Chromecast/Google Home, Sonos and UPnP/DLNA renderers. The native AMP receiver is distinct from claiming every AMP app is a certified native Google Cast receiver. Track per-endpoint capabilities and implement transport-specific sender/receiver support explicitly rather than showing unsupported controls.

Separate protocol support from codec/container support. Prefer direct play when the target supports the source, otherwise transcode to a negotiated compatible stream. Support broad source formats through the decoder pipeline, without promising that every target accepts every codec natively. Codec/sample-rate/channel limits vary by receiver/model. Sonos grouping, Google speaker groups, DLNA renderers and native AMP low-latency endpoints require separate tests. Most compatible playback is a goal; universal cross-protocol synchronized zero-latency playback is not an assumed property.

Preserve the completed live master mix, one playback owner per stream, cue privacy, output selection, gain, station/session identity, loop prevention and source provenance when relaying between endpoints. Show measured versus target latency, adaptive quality, queue/buffer state and reconnect status. Receiving playback through a browser may need an explicit user Play gesture; mobile receiving must honor foreground/audio-focus/platform lifecycle requirements. High-performance native AMP transport and compatibility-oriented external-speaker streams can use different negotiated buffer/codec profiles behind one output picker.

## Station hosting and endpoint ownership: owner clarification

Desktop and Android are sending/receiving endpoints. Each installation may own only ONE active Cast session at a time: send OR receive, not simultaneous sending and receiving and not multiple concurrent station hosts. Replacing a session must be explicit and stop/release the old owner; reconnect must not steal a newer session. Ordinary local playback/cue routing must remain clearly distinguished from the Cast session.

Desktop and Android may host LIVE stations only (their currently performed/played audio). Only the server hosts automated stations, for BOTH normal playlists and Smart Playlists. Clients receive those automated stations from the server; syncing/downloading a playlist does not grant the client an automated station-host role. Local playback and DJ use of locally available media remain separate from hosting an automated station.

Normal playlists and Smart Playlists can be created/edited on desktop and Android and automatically synchronize to the server, with edits/renames/order/rules synchronized back to clients. Keep stable IDs, revision/conflict handling and offline outbox replay. The server executes playlist-backed station scheduling and automation. Playlist metadata availability on a client, offline media availability, local DJ playback and automated station hosting are separate capabilities.

Server may host multiple isolated automated stations. Each connected desktop/mobile endpoint still selects just one active sending OR receiving Cast session. Do not enable endpoint relay loops, background client-hosted automated playlist stations or hidden simultaneous sessions. This clarification narrows earlier general statements about universal sending/receiving: both directions are supported as modes, never concurrently on a client installation.

## Library, playlist builder and Auto Mix ordering: owner clarification

Keep the library organized/browsable as FOLDERS. In the DJ workspace, ordinary Playlists and Smart Playlists replace crates; do not introduce a separate crate collection or replace the folder library with playlists.

The playlist builder must make it easy to find desired music, browse/filter the collection, audition candidates and assemble/review a list. Ordinary playlists have explicit saved membership and ordering, with clear add/remove/reorder actions. Smart Playlists have saved rules/sources and a visible eligible-song preview; matching songs are distinct from execution order. Search/filter/selection should preserve the current draft, scroll and playback state. Broader filter/layout details need real-screen UX validation rather than an unreviewed universal layout.

Auto Mix selection policy is explicit by playlist type:

- REGULAR PLAYLIST: follow saved track order. Mixing/transition preparation may adapt the handoff, but compatibility scoring must not silently reorder or substitute the next track. With Shuffle OFF, playlist order wins over BPM/key/energy preferences. If the next track is unavailable, report it and apply a documented skip/stop policy without silently turning the list into a Smart Playlist.
- REGULAR PLAYLIST + SHUFFLE ON: use a shuffled traversal of that playlist's members. Retain membership and avoid unintended repeats within a pass. Smart harmonic/energy ranking is not implicitly enabled by Shuffle.
- SMART PLAYLIST: the DJ may rank/select the best next eligible track using prepared tempo/key/energy/phrase information and the configured mixing style. Preserve saved source/filter/exclusion rules, repeat controls, manual requests/locks and honest missing-analysis fallbacks. Execution ordering may change; shared rule definitions remain intact.

The policy applies consistently to desktop Auto Mix and server-hosted automated stations. Mobile receives the same playlist types/semantics; its lack of analysis write permission is unrelated. Sync ordinary order and explicit Shuffle state according to documented ownership; do not silently publish a transient Smart Playlist execution order over the user's saved playlist. Tests must prove that a less-compatible next song remains next in ordered mode, Shuffle uses only members, and Smart ranking never violates eligibility.

## Data model

- Library tracks and paths are associations, not the identity of a musical recording. Exact file identity starts with SHA-256; different encodings/retags require separately validated audio-identity mapping before reuse. Artist/title alone is never enough, especially for DJ edits and remixes.
- Store immutable observations with source hash, producer, producer version, settings hash, kind, and content-derived record ID. Keep conflicting measurements and provenance; do not replace one provider's result with another without review.
- Distinguish provider hints, native measurements, prepared summaries, reviewed grids/cues, and stem manifests. A BPM/key lookup is not an exact beatgrid or a stem file.
- A resolved preparation references its source observations and reviewed revisions. Desktop edits need revision checks and explicit authorship. Automated refinement must preserve reviewed corrections.
- Audio/stem objects live in managed storage; the database references validated objects/checksums instead of duplicating audio per device or embedding it in ordinary metadata responses.
- One server owns the working database on local storage. Clients use paged APIs and cached read-only snapshots. Do not put a writable shared SQLite/WAL database on SMB.

## Implemented in this branch

Original Rust module `amp_core::knowledge` provides an additive device-local SQLite store with immutable, idempotent observations, indexed source lookup, bounded pages/batches, schema/application identity checks, and record integrity checks. Different outputs, versions and settings coexist.

`amp-cast` exposes authenticated routes:

- `GET /api/knowledge/status`
- `GET /api/knowledge/audio/{lowercase_sha256}?limit=50&after=RECORD_ID`
- `POST /api/knowledge/import` with `{ "offset": 0, "limit": 50 }`

Import processes at most 100 already-loaded preparation summaries per request. It does not scan, decode, rehash, upload, change source music or modify playback. Follow `next_offset` until null. This is a snapshot backfill, not a claim that every on-disk track has been imported.

New completed server analysis also indexes its preparation summary into `knowledge.ampdb` beside the server configuration. Knowledge indexing errors are reported separately from analysis failure and do not discard completed preparation. A missing configuration directory disables these operations explicitly.

The summary includes measured/confidence metadata and review flags, but excludes paths, personal cues and source/stem audio. Its source identity is inherited from saved preparation, not freshly verified during import. Therefore summaries explicitly have `automatic_reuse_eligible=false`. The store is an evidence foundation; it does not yet replace the portable catalog or feed Auto Mix directly.

The new API accepts no arbitrary client-written observation/document. Its import command asks the server to index its own preparation. Dedicated desktop writer credentials and revision-checked correction endpoints are not implemented yet. Existing station authentication applies; do not claim a global desktop/mobile role system has shipped.

## Remaining implementation sequence

1. Source adapters feed one bounded server queue. Wait for stable/completed downloads; ignore partial files, excluded speech/audiobooks and unsupported inputs; give each item one identity/versioned job. Reconcile moves, duplicates, retries and rescans rather than continually redoing completed work.
2. Add identity-verified native feature/stem observations, model/settings manifests, resumable preparation, and migration from current catalog. Cache hits must bypass expensive DSP and preserve manual data.
3. Resolve observations plus reviewed desktop edits into versioned preparation. Add explicit writer authorization and optimistic revision checks; mobile receives read-only analysis scope. Retain rollback/export and offline caches.
4. Add provider adapters with exact-version/duration matching, provenance, positive/negative caches, rate limits, and bounded retries. Start with existing tags/open metadata. Paid jobs and audio/fingerprint uploads require an explicitly selected provider/configuration.
5. Desktop Auto Mix and Android consume the same resolved records. Prepared stems/grids must be present and verified; otherwise use an honest fallback. Validate latency, quality and phase alignment; do not synthesize confidence or silently fetch heavy assets during playback.
6. Benchmark 1k/10k/30k catalog reads and queue writes, then compare rendered transition fixtures and real listening. UI must show real preparation state and why a feature is unavailable.

## Open-source engine research boundaries

AMP's server/core are already Rust. Study upstream architecture and documented algorithms, then implement/test bounded improvements. A Rust translation of GPL source remains a port with its upstream obligations; do not silently place it under AMP's MIT header. This branch contains no copied/translated Mixxx, Rubber Band or OwnTone code and does not claim to port their complete engines.

- Mixxx engine architecture: https://github.com/mixxxdj/mixxx/wiki/Developer-Guide-Engine (real-time thread discipline and separate output buses).
- Rubber Band technical notes: https://breakfastquay.com/rubberband/technical.html (time-stretching/transient/phase problems; not a claim that AMP implements the same engine).
- OwnTone documentation: https://owntone.github.io/owntone-server/ (server control and output architecture).
- SQLite network/WAL restrictions: https://www.sqlite.org/useovernet.html and https://www.sqlite.org/wal.html.

Stem ML inference should initially use an isolated, versioned open-source worker. Rewriting an inference framework or model into Rust is a separate benchmarked project, not a prerequisite for a Rust scheduler/database or a promise of faster processing.
